# 1. 记录架构决策

## 状态

提议 (Proposed)

## 上下文

DocRetrieval 服务涉及多个关键技术决策（语言栈、向量库、解析器选型等），这些决策对后续开发和维护影响重大。为了：
1. 记录决策背景与理由
2. 便于新成员理解历史选择
3. 便于后续评估是否需要调整决策
4. 满足 [checklist.md](../checklist.md#L146) 的验收要求

我们需要一个轻量级的决策记录机制。

## 决策

使用 **Architecture Decision Records (ADR)** 格式记录所有关键架构决策，存储在 `docs/adr/` 目录下。

## 备选方案

1. **仅在 spec.md 中记录** - 不独立记录，直接写在技术规格里
   - 优点：文档少
   - 缺点：决策理由容易被淹没，难以追溯历史调整
2. **PR 描述记录** - 仅在 PR 里写决策理由
   - 优点：轻量
   - 缺点：PR 历史查找困难，没有统一视图
3. **ADR 文档** - 独立的 ADR 文件
   - 优点：格式统一，易于查找和维护
   - 缺点：多一个文档要写

## 理由

选择 ADR 是因为：
- 项目有多个复杂技术决策，值得单独记录
- [checklist.md](../checklist.md) 明确要求"关键决策有 ADR 记录"
- ADR 是行业通用做法，团队学习成本低

## 后果

- 每个关键决策都要有对应的 ADR 文档
- 决策变更时需要新增 ADR（而不是修改旧 ADR）
- 在 [checklist.md](../checklist.md) 验收时需要检查 ADR 完整性
