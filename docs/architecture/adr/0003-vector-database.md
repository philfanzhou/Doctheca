# 3. 向量库选择

## 状态

已决定 (Accepted)

## 上下文

DocRetrieval 服务需要语义召回能力，用于：
1. 查找与查询词语义相近的句子/题目
2. 支持混合检索（精确匹配 + 语义召回）

需要评估不同向量库方案的成熟度、易用性、与现有技术栈的兼容性。

## 决策

选择 **Qdrant** 作为向量数据库。

选项：
1. ~~**Qdrant**（推荐）~~ - 专业向量数据库 ✅ 已选
2. **pgvector** - PostgreSQL 扩展，利用现有数据库

## 备选方案分析

### 方案 A：Qdrant ✅
- **优点**：
  - 专为向量检索设计，性能更好
  - 功能丰富（过滤、索引类型、距离度量等）
  - 生态成熟
- **缺点**：
  - 新增中间件依赖
  - 需要额外运维成本

### 方案 B：pgvector
- **优点**：
  - 利用现有 PostgreSQL，无需新中间件
  - 数据一致性好（与元数据同库）
  - 运维简单
- **缺点**：
  - 向量检索性能不如专用向量数据库
  - 功能相对有限

## 理由

选择 Qdrant 是因为：
- 项目需要混合检索（精确匹配 + 语义召回），Qdrant 的过滤+向量检索组合能力更成熟
- .NET 生态对 Qdrant 有官方/社区 SDK 支持
- 虽然新增中间件，但 Qdrant 部署简单（单容器即可），运维负担可控
- 语义召回是核心能力，专用向量库能提供更稳定的召回质量

## 后果

- 需要部署 Qdrant 服务（Docker 容器）
- .NET 服务需集成 Qdrant SDK
- 删除文档时需同步清理 Qdrant 中对应向量条目
- 未来如需更换向量库，需抽象向量存储接口
