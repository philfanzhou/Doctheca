# DocRetrieval 业务流程设计文档

> 本文档只描述**业务层面**的流程：参与者、流转顺序、状态、异常分支、衔接关系。
> 业务需求（做什么、做到什么程度）见 [requirements.md](./requirements.md)；
> 技术实现（用什么协议、什么存储、什么排序）见 [spec.md](./spec.md)。

## 1. 文档定位

| 文档 | 视角 | 回答的问题 |
|------|------|------------|
| [requirements.md](./requirements.md) | 业务需求 | 做什么、为谁做、做到什么程度 |
| **process.md（本文）** | 业务流程 | 谁在什么时机做什么、状态如何流转、错了怎么办 |
| [spec.md](./spec.md) | 技术规格 | 用什么协议、什么存储、什么算法实现上述流程 |

> 业务变更优先改 `requirements.md`，再驱动本文档与 `spec.md` 同步；不要在 `spec.md` 里夹带流程描述。

## 2. 业务角色与边界

| 角色 | 性质 | 与本服务的关系 |
|------|------|----------------|
| **上游业务系统** | 消费者（其它后端微服务） | 调用本服务的导入 / 查询 / 状态三类接口 |
| **本服务（DocRetrieval）** | 提供者 | 只响应上游请求，不主动外呼 |
| **被处理的文档** | 业务对象 | 由上游交付、由本服务解析并建立可检索结构 |
| **终端用户（学生 / 教师 / 家长）** | 最终受众 | **不直接调用本服务**，由上游业务系统服务 |

**关键约束**：

- 本服务**永远不直面终端用户**，没有用户态、登录态、权限态。
- 本服务**不主动通知**上游（不推送、不回调、不发事件），仅在被查询时给出当前状态。
- 上游负责把"用户行为"翻译成"对 DocRetrieval 的请求"。

## 3. 业务流程总览

本服务对外暴露**三条业务流**，分别对应 `requirements.md §3.2` 的三类能力：

```
┌──────────────────────────────────────────────────────────────────┐
│                       DocRetrieval 业务流程                       │
│                                                                  │
│   ① 文档导入流    ② 文档查询流    ③ 导入状态跟踪流                │
│                                                                  │
│  ┌─────────┐  导入   ┌──────────┐  查询  ┌──────────┐            │
│  │ 上游系统 │ ──────▶ │ DocRetrieval │ ◀────── │ 上游系统 │            │
│  └─────────┘         └──────────┘  状态  └──────────┘            │
│       │                │     ▲         │                          │
│       │                │     │         │                          │
│       ▼                ▼     │         ▼                          │
│   收集文档         解析 / 索引  │     消费命中                      │
│   + 元数据        （异步处理） │   （展示 / 组装）                  │
│                                  │                                 │
└──────────────────────────────────────────────────────────────────┘
```

三条流的**关系**：

- ① 是 ② 的**前置**：没有被导入并"就绪"的文档，不能被查询。
- ③ 是 ① 的**伴随**：导入是耗时异步过程，上游必须能跟踪其状态。
- ① 与 ② 互不阻塞：导入进行中时，**已就绪**的文档仍可被查询。

## 4. 核心业务流程

### 4.1 文档导入流

**业务目标**：把上游持有的一份英文文档（PDF / Word / PPT，含扫描件）转化为"可被查询接口消费的检索底座"。

#### 4.1.1 触发时机

由上游业务系统决定，常见场景包括：

- 教材 / 真题录入后台"上传文件"动作
- 运营批量导入一批真题
- 周期任务把新到的资料自动入索引

#### 4.1.2 流程步骤

| 步骤 | 主体 | 业务行为 |
|------|------|----------|
| 1 | 上游 | 收集"一份文档文件 + 元数据"（教材名 / 学科 / 年级 / 年份 / 标签等，可选） |
| 2 | 上游 | 调用本服务**导入接口** |
| 3 | 本服务 | 校验入参（类型 / 大小 / 是否英文等业务层校验），生成**导入任务 ID** 并立即返回 |
| 4 | 本服务 | 异步执行：解析 → 抽取页码 / 段落 / 句子 / 题目 → 建索引（具体技术细节见 `spec.md`） |
| 5 | 上游 | 拿到任务 ID 后，进入"导入状态跟踪流"（见 §4.3） |
| 6 | 上游 | 当状态变为"成功"后，可对该文档发起查询 |

#### 4.1.3 关键业务规则

- **导入是异步的**：本服务只承诺"收到并受理"，不承诺"立即可查"。
- **元数据是过滤维度**：上游传入的教材名 / 学科 / 年级 / 年份必须**全量透传至查询阶段**，作为命中过滤的合法维度。
- **不支持的格式**必须立即拒绝（同步返回失败），不得进入异步阶段。
- **同一份文档重复导入**按业务策略处理：常见策略为"幂等更新"（按内容指纹去重，相同内容只保留一份最新）。

#### 4.1.4 时序图（业务视角）

```
上游系统                      DocRetrieval
   │                              │
   │  ① 收集文件 + 元数据          │
   │  ──────────────────────────▶ │  ② 同步返回 导入任务ID
   │  ◀─────────────────────────  │
   │                              │  ③ 异步：解析 → 抽锚点 → 建索引
   │                              │      ┌──────┐
   │                              │      │ 进行中│
   │                              │      └──┬───┘
   │                              │         │
   │                              │      ┌──▼───┐    ┌──────┐
   │                              │      │ 成功  │ 或 │ 失败  │
   │                              │      └──────┘    └──────┘
   │  ④ 轮询状态（§4.3）           │              │
   │  ──────────────────────────▶ │
   │  ◀─────────────────────────  │
   │  ⑤ 成功后，对该文档发起查询     │
```

### 4.2 文档查询流

**业务目标**：上游传入"一个词 / 一个短语"，本服务返回该词 / 短语在哪些已就绪文档的哪一页、所在的句 / 题是什么。

#### 4.2.1 触发时机

由上游业务系统决定，常见场景：

- 错题 / 生词本点击"查看原句"
- 教材定位（"这个生词出现在哪本教材哪一页"）
- 真题推送（"这道题在原卷里长什么样"）
- 批量 PDF 导出（"把跟该词相关的句子收集成 PDF"）

#### 4.2.2 流程步骤

| 步骤 | 主体 | 业务行为 |
|------|------|----------|
| 1 | 上游 | 准备入参：`query`（必填，单词或短语）+ 可选过滤（教材名 / 学科 / 年级 / 年份 等） |
| 2 | 上游 | 调用本服务**查询接口** |
| 3 | 本服务 | **归一化**（大小写、词形；具体规则见 `requirements.md §4.2` 与 `spec.md`） |
| 4 | 本服务 | 执行检索（精确匹配 + 可选语义召回） |
| 5 | 本服务 | **去重**（同一页同句 / 同题的多处出现合并为一条） |
| 6 | 本服务 | **排序**（按相关度） |
| 7 | 本服务 | 构造**命中列表**返回上游 |
| 8 | 上游 | 消费命中：在自己的产品里展示"原句" / 还原"题号" / 收集"导出条目" |

#### 4.2.3 关键业务规则

- **短语必须完整命中**：查 "take notes" 不得返回 "take ... notes ..." 这种被拆碎的命中。
- **粒度由文档类型决定**（详见 `requirements.md §4.2`）：
  - 教材 / 讲义类 → 关联文本是**句子**。
  - 试卷类 → 关联文本是**题目文本**。
- **大小写与词形归一化**是本服务责任，上游不需要提前处理。
- **过滤维度的语义**由上游传入的元数据决定；本服务不做"猜你想查哪个学科"。
- **未就绪的文档**不参与查询：导入未成功的文档不能被查到。
- **无命中**不是错误：返回空列表即可，上游决定如何展示。

#### 4.2.4 时序图（业务视角）

```
上游系统                      DocRetrieval
   │                              │
   │  ① 收集 query + 可选过滤     │
   │  ──────────────────────────▶ │  ② 归一化
   │                              │  ③ 检索（精确 + 语义）
   │                              │  ④ 去重 + 排序
   │  ◀─────────────────────────  │  ⑤ 返回命中列表
   │  ⑥ 消费命中（展示 / 组装）    │
```

#### 4.2.5 命中项业务字段

每条命中**至少**包含（详细字段命名见 `spec.md`）：

| 字段 | 业务含义 |
|------|----------|
| 文档名 | 该命中来自哪份文档 |
| 页码 | 出现在第几页 |
| 关联文本 | 该词 / 短语所在的**句子**（教材类）或**题目文本**（试卷类） |

可选字段（业务上允许出现，但本服务不强约束字段名）：

| 字段 | 业务含义 |
|------|----------|
| 文档 ID / 任务 ID | 命中所属导入任务的标识 |
| 学科 / 年级 / 年份 | 用于二次过滤或前端展示 |
| 题号（试卷类） | 题目在试卷中的编号 |
| 相关度评分 | 用于上游做二次排序或解释 |

### 4.3 导入状态跟踪流

**业务目标**：让上游能确认"那份文档导入得怎么样了"。

#### 4.3.1 触发时机

- 上游在调用导入接口拿到任务 ID 之后，**周期轮询**或**按需查询**。
- 不存在"回调 / 推送"形式的通知。

#### 4.3.2 流程步骤

| 步骤 | 主体 | 业务行为 |
|------|------|----------|
| 1 | 上游 | 拿任务 ID 调用**状态查询接口** |
| 2 | 本服务 | 返回当前状态（进行中 / 成功 / 失败）+ 业务可见的进度信息（如"解析中"、"建索引中"） |
| 3 | 上游 | 根据状态决定下一步：继续轮询 / 标记文档可消费 / 触发重试 / 告警 |

#### 4.3.3 关键业务规则

- 状态值必须**单调收敛**：进行中 → 成功 / 失败，不得在成功后回退为进行中。
- 失败时必须给出**业务可读**的失败原因分类（格式不支持 / 文件损坏 / OCR 失败 / 索引失败 等），但**不暴露**技术栈细节。
- 状态查询的频率与节奏由上游决定，本服务不限制（业务层面）。
- 已成功的任务其状态不可变；如需"再导入一次"，必须创建新任务。

## 5. 业务状态机

### 5.1 导入任务状态机

```
                  ┌──────────┐
                  │  待处理   │（任务已受理，尚未开始解析）
                  └────┬─────┘
                       │ 开始解析
                       ▼
                  ┌──────────┐
        ┌────────▶│  进行中   │（解析 / OCR / 建索引 中某一阶段）
        │         └────┬─────┘
        │              │ 完成
        │              ▼
        │         ┌──────────┐
        │         │  成功     │（文档已"就绪"，可被查询）
        │         └──────────┘
        │ 失败重试
        │              │ 失败
        │              ▼
        │         ┌──────────┐
        └─────────│  失败     │（带失败原因，文档不可被查询）
                  └──────────┘
```

**业务规则**：

- 状态终态：`成功` / `失败`；两者不可互相转化。
- `失败` 状态下，上游可选择**新建任务**重试（业务层面），不修改原任务。
- 任意非终态的查询返回 `进行中`（及当前阶段信息），不会出现"未知状态"。

### 5.2 文档可消费状态

文档"能否被查询到"由其**最新一个成功导入任务**决定：

| 状态 | 含义 | 上游行为 |
|------|------|----------|
| 未就绪 | 有任务但未成功，或没有任务 | 不得在面向用户的功能中暴露"可查" |
| 已就绪 | 至少一个导入任务处于"成功" | 可作为查询目标 |
| 已下架 | 文档被运营下线（业务后续扩展） | 同"未就绪" |

> 状态切换由导入任务的成败驱动，本服务不维护独立的"上下架"流程（首版）。

## 6. 异常与降级分支

| 异常场景 | 业务流程表现 | 业务处理建议 |
|----------|--------------|--------------|
| 文件格式不在 §3.1 范围 | 导入接口**同步拒绝** | 上游立即提示"该格式暂不支持" |
| 文件损坏 / 解析失败 | 任务进入 `失败`，带原因"解析失败" | 上游可选择重试或人工介入 |
| 扫描件 OCR 失败（质量过差） | 任务进入 `失败`，带原因"OCR 失败" | 上游可提示用户"请上传更清晰的扫描件" |
| 索引失败 | 任务进入 `失败`，带原因"索引失败" | 上游可触发重试 |
| 查询无命中 | 正常返回**空列表**（非错误） | 上游展示"暂无原文命中" |
| 上游传入空 query / 非英文 | 同步拒绝（业务校验） | 上游在校验层提示 |
| 上游高频轮询状态 | 业务不限制 | 由 `spec.md` 在技术层做频率保护 |
| 文档正在导入中、已被查询请求命中过滤 | 查询正常返回（**不阻塞**） | 上游不必等待导入完成 |

## 7. 与上游业务流程的衔接

本服务在更大的"英语错题分析与词汇学习系统"中是被调用方。下表列出上游典型业务流与本服务流程的对应关系（业务对应关系来自 `requirements.md §9`）：

| 上游业务流 | 对应的本服务流程 | 备注 |
|------------|------------------|------|
| 生词自动提取 | 文档查询流 | 上游拿到生词后逐个查"原句" |
| 教材定位 | 文档查询流（带过滤） | 上游携带教材 / 学科 / 年级 / 年份 |
| 原句展示 | 文档查询流（命中项） | 上游把 `关联文本` 渲染到产品里 |
| 真题推送 | 文档查询流（试卷类） | 上游从命中项的 `关联文本` 还原"题目" |
| PDF 导出 | 文档查询流（批量） | 上游循环调用查询接口，把命中项组装成 PDF |

> 上游必须**自行**实现上述业务流程；本服务**不感知**用户态、UI 与导出格式。

## 8. 业务不变式（硬约束）

下面这些是**业务层面的承诺**，技术实现不得绕过：

1. **每条命中可指回原文**：返回的 `关联文本` 必须是文档中真实存在的句子 / 题目。
2. **短语查询不拆碎**：返回的命中中，`关联文本` 必须**完整包含**用户传入的短语。
3. **粒度不串台**：教材类返回句，试卷类返回题；不允许在教材上返回"题"，也不允许在试卷上返回"段落"。
4. **未就绪不可查**：未成功导入的文档不能出现在任何查询结果中。
5. **状态单调收敛**：导入任务一旦成功，不得再变为失败（即使后续索引服务故障，本服务也必须以"任务视角"对外负责）。
6. **本服务永远不持有用户态**：任何调用方认证 / 权限 / 配额都由上游负责。

## 9. 业务流程的扩展点

下面这些是**业务允许的未来扩展**，但**不在首版范围**。扩展前应先回到 `requirements.md` 更新业务边界，再回到本文档补充流程，再驱动 `spec.md` 变更。

| 扩展方向 | 流程层面的变化 |
|----------|----------------|
| 新增文档类型（如图片型试卷） | 在导入流 §4.1 增加类型分支；在 §5.1 状态机不变 |
| 多语种（中文 / 其它） | 在导入流 §4.1 增加语言校验；在 §4.2 归一化规则增加语言维度 |
| 上游事件回调（替代轮询） | 在 §4.3 增加"订阅"分支，状态机不变 |
| 题目级 / 段落级粒度切换 | 在 §4.2.5 增加可选粒度参数，命中项结构不变 |
| 文档上下架 | 引入"已下架"状态到 §5.2；与导入任务状态解耦 |

## 10. 变更规则

- **业务范围扩大**（新增能力 / 新增文档类型 / 新增语种）：先改 [requirements.md](./requirements.md)，再改本文档，最后改 [spec.md](./spec.md)。
- **业务流程优化**（不变更业务范围，仅优化步骤顺序 / 异常分类）：直接改本文档，并在 [checklist.md](./checklist.md) 中追加对应验收项。
- **任何技术实现上的优化**（不改变业务流）：只改 [spec.md](./spec.md)，**不得回流到本文档**。
